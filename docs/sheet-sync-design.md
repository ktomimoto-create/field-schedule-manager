# スプレッドシートの行動予定表を本番へ自動で取り込む仕組み（設計案）

- 作成: 2026-10-19（上田さんの回答をもとに）
- 状態: 案（実装前。DB の表と関数の追加は富本さんに流してもらう必要がある）

## 1. 何をするか

Google ドライブの「1．行動予定表」（`2026年/10月/1019` のように日ごとにスプレッドシートがある）を、
**Google のクラウド（Apps Script）が定期的に読み、本番の予定表（schedules）へ送る**。
PC が止まっていても動く。シートは読むだけで書き換えない。
FE動態のアルコールチェックが、同じフォルダを同じやり方ですでに読んでいる（`fe-dotai/scripts/alcohol/apps-script/fd-ac-sheets.gs`）。

## 2. 決めたこと（2026-10-19 上田さんの回答）

| 項目 | 決定 |
|---|---|
| 正本 | **アプリでも直せる**。アプリで直した項目は、取り込みで上書きしない |
| シートから消した行 | **キャンセルにする**（消さない） |
| 取り込む範囲 | **今日・明日のシート**（定期）／**10 月分すべて**（1 回だけさかのぼる）／**1 行目の休暇・健康診断など**（休暇・社内予定として入れる） |

## 3. 流れ

```
Apps Script（上田さんの Google アカウント・5 分ごと。夜は 15 分ごと）
  └ 今日と明日のシートを開く（無ければ何もしない）
  └ 3 行目が見出し、4 行目からが予定。1 行目は休暇・健診など
  └ 本番 Supabase の関数 fsm_sync_sheet_day(トークン, 日付, 行, 1 行目) を呼ぶ
         └ 行ごとに「前回取り込んだ値」と比べて、追加・更新・キャンセルを決める
         └ 結果（追加 n・更新 n・キャンセル n・食い違い n）を記録 → アプリに「最終取り込み 12:05」と出す
アプリ（予定表・月間予定表・動態マップ）
  └ 既存の Realtime で自動で反映（画面の再読み込み不要）
```

## 4. 行の突き合わせ（どの行がどの予定か）

シートの行には番号（ID）が無いので、次の順で探す。

1. **前回と同じ鍵**: 日付 ＋ 号機（無ければ物件名）＋ 対応者 ＋ 同じ組み合わせの何番目か
2. 1 で見つからない行は、**同じ日・同じ号機と物件名で、今回のシートに無くなった行**を探す（対応者や時間を変えた行を「同じ予定の変更」として扱う）
3. それでも無ければ**新しい予定**として追加

さかのぼり（10 月分）では、すでに本番にある予定（10/15 の 62 件など、手で取り込んだもの）も 1・2 で探して**結び付ける**。二重に入れない。

## 5. 「アプリでも直せる」の仕組み（3 者比較）

取り込んだときのシートの値を、予定ごとに別の表へ覚えておく（`fsm_sheet_rows.synced`）。次の取り込みで、項目ごとに:

| 本番の今の値 | シートの新しい値 | どうするか |
|---|---|---|
| 前回取り込んだ値のまま | 変わった | **シートの値で更新** |
| アプリで直されている | 変わっていない | **アプリの値を残す** |
| アプリで直されている | 変わった | **アプリの値を残し、「食い違い」として記録**（予定表に印を出す） |

- 結果・開始/完了時刻・報告メモ・FE のボタン記録・並び順は**取り込みの対象外**（アプリ側のもの）
- シートの「結果」が「キャンセル」なら予定をキャンセルにする。「完了」は、アプリの結果が空のときだけ入れる

## 6. シートから消えた行

本番の予定は**消さずにキャンセル**にする（状況 = cancelled、備考に「シートから削除（10/19 12:05）」）。
シートに戻ってきたら、キャンセルを外して元に戻す。

## 7. 1 行目（休暇・健康診断など）

例: `健康診断：下田（8:30）池宮(10:00)…　棚卸：淺沼/佐藤　休暇：藤田/FR金谷/岡﨑/富本/清水/ビル`

- 「ラベル：名前/名前…」の形を読み、ラベルが**休暇**なら休暇、**種別マスタの社内予定（is_internal）にある名前**（健康診断・棚卸など）ならその社内予定として、名前ごとに 1 件入れる。かっこの時刻は時間に入れる
- 2 行目の「障害：…」・3 行目の担当者の並び・「同行：…」は今回は取り込まない（アルコールチェックが別に使っている）
- 名簿に無い名前（「ビル」など）は名前の文字だけで入れる

## 8. 対応者の名寄せ

アプリの `findStaffByName` と同じ考え方を DB 側の関数で行う: 完全一致 → 空白を除いて一致 → 異体字（﨑→崎）をそろえて苗字の前方一致が 1 人だけ。
2026-10-19 のお試しで、アプリ側は「高田」（名簿は空白なしの「高田晴規」）と「FR岡﨑」を解決できなかったので、DB 側ではこの 2 つを確かめる。

## 9. DB に足すもの（既存の表は変えない）

| 名前 | 中身 |
|---|---|
| `fsm_ingest_tokens` | Apps Script のトークンのハッシュ（トークンそのものは保存しない） |
| `fsm_sheet_rows` | 予定 ID ↔ シートの行の鍵・前回取り込んだ値（jsonb）・最後に見えた時刻・食い違いの印 |
| `fsm_sync_runs` | 取り込みの記録（日時・対象日・追加/更新/キャンセル/食い違いの件数・エラー） |
| 関数 `fsm_sync_sheet_day(p_token, p_date, p_rows, p_header)` | security definer。トークンを確かめてから上の 4〜7 を行う |

すべて RLS を有効にし、anon からは関数だけ呼べる（関数の中でトークンを確かめる）。
予定（schedules）への書き込みは関数の中だけ。拠点は東京として入れる。

## 10. 気をつけること

- **手での取り込み（スプレッドシートから貼り付け）との二重**: 自動を始めたら、行動予定表の手での取り込みはやめる。運用している人（下田さん・富本さんなど）と合意してから始める
- シートの形（列の並び・3 行目の見出し）が変わると読めなくなる → 見出しの文字で列を探し、見つからなければ取り込まずにエラーを記録する
- 同じ日に同じ号機・同じ対応者が 2 行（例: 同じ物件の別作業）あるときは「何番目か」で区別する。行の順番を入れ替えると別の予定として扱われることがある（その場合は 4 の 2 で拾う）
- お試しモードには入らない（本番だけ）

## 11. 進め方（案）

1. DB の SQL（`sql/sheet_sync.sql`）と確認用 SQL を書く → 富本さんに流してもらう
2. Apps Script（`scripts/sheet-sync/sheet-sync.gs`）を書く → 上田さんのアカウントで `setup()` を 1 回実行 → 出たハッシュを DB に登録
3. まず **さかのぼりを「試し」で実行**（DB を変えずに、追加・更新・結び付けの件数だけ返す）→ 件数を見て問題なければ本実行
4. 定期実行を始める。アプリのヘッダーに「最終取り込み」と食い違いの件数を出す
